- Symptôme: worktree git créé côté Windows illisible depuis WSL2 (`git status` échoue "not a git repository") | Cause: `.git` pointer + `.git/worktrees/<name>/{gitdir,commondir}` contiennent des chemins Windows (`C:/Users/...`), invalides pour WSL2 | Correctif: split systématique — npm/cargo/tauri toujours via `wsl.exe -e bash -lc "..."`, TOUTES les commandes git toujours côté Windows (Bash tool direct, pas wsl.exe)

- Symptôme: process `cargo`/`tauri dev` lancé en `nohup ... & disown` dans un `wsl.exe -e bash -lc "..."` meurt quelques secondes après le retour de l'appel d'outil | Cause: WSL2 arrête l'instance légère quelques secondes après la fin du dernier process attaché à la session lancée par `wsl.exe`, tuant tout ce qui a été détaché | Correctif: pour tout process long (build, dev server), le lancer en foreground DIRECT comme commande principale d'un appel Bash marqué `run_in_background: true` côté outil (pas de nohup/disown interne) — ça garde WSL2 vivant tout le temps nécessaire

- Symptôme: `pgrep -f "target/debug/tauri-app"` matche parfois le mauvais process (wrapper cargo/npm au lieu du vrai binaire exec'd) | Cause: pgrep -f matche la ligne de commande complète, plusieurs process peuvent contenir la sous-chaîne | Correctif: toujours croiser avec `ps -ef | grep target/debug` et vérifier le cmdline exact (`cat /proc/<pid>/cmdline`) avant de faire confiance à un PID pour la vérification GUI

- Symptôme: sous-agent rapporte "DONE" avec vérification affirmée mais pas réellement faite (ex: build encore en cours de compilation au moment du rapport) | Cause: sous-agents pressés de conclure, ou contexte insuffisant sur la durée réelle d'un cold build Tauri+webkit2gtk (10-20+ min) | Correctif: JAMAIS accepter un rapport de sous-agent comme preuve suffisante — toujours re-vérifier indépendamment (relire commit réel via `git show`, re-lancer les tests soi-même) avant de marquer une tâche "revue qualité" comme approuvée

- Symptôme: revue de code trouve régulièrement des lacunes réelles (validation trop permissive, type `unknown` au lieu de type strict, gap de cohérence entre store et type système) même sur du code qui "matche le plan exactement" | Cause: le plan lui-même a des angles morts (ex: `importTheme` du plan original ne validait pas les 11 clés requises) | Correctif: ne jamais sauter la revue qualité même quand la revue spec est ✅ — les deux revues trouvent des choses différentes, garder les deux systématiquement

- Symptôme: agent de revue de code interrompu en plein milieu par une erreur de connexion API | Cause: coupure réseau/infra transitoire | Correctif: renvoyer un message à l'agent (SendMessage) lui demandant son rapport final complet plutôt que de relancer un nouvel agent depuis zéro (économise le contexte déjà construit)

- Symptôme: agent atteint la limite de dépense mensuelle en plein milieu d'une revue | Cause: quota/facturation, pas un bug | Correctif: ne pas contourner — attendre que l'utilisateur relance la session (login), puis relancer la même tâche depuis zéro avec un nouvel agent (le contexte de la revue précédente était perdu, pas de reprise possible pour un agent qui n'a jamais rendu son rapport)

- Symptôme: `sysinfo::System::new_all()` reconstruit à chaque appel de commande Tauri → `cpu_usage()` reste bloqué à ~0% en permanence | Cause: sysinfo calcule l'usage CPU par delta entre deux refresh sur la MÊME instance ; recréer `System` à chaque appel ne laisse jamais d'échantillon précédent | Correctif: garder UNE instance `System` en `tauri::State<Mutex<System>>` managée, faire des refresh ciblés (`refresh_cpu_usage`, `refresh_memory`, etc.) sur l'instance existante à chaque commande, jamais `System::new_all()` répété. S'applique à toute future commande Tauri qui lit des métriques temps réel (Tasks 9+).

- Symptôme: `npm run tauri build` échoue avec `failed to read file '/mnt/c/Users/Momo/Desktop/NiTruX/.../app_hide.toml': No such file or directory` alors que le repo est maintenant sous `D:\Projet\NiTruX` | Cause: cache `target/` accumulé lors d'un déplacement historique du repo (Desktop → D:\Projet), un script de build en cache référence encore l'ancien chemin absolu | Correctif: `cargo clean --release -p nitrux -p tauri -p tauri-build` (nettoyage ciblé, ~900 Mo) plutôt qu'un `rm -rf target/` complet (33+ Go, rebuild bien plus long) — suffit à invalider le cache périmé sans perdre la compilation des dépendances
- Symptôme: notification de tâche background "completed (exit code 0)" alors que le build a en réalité échoué | Cause: la commande était pipée (`... | tail -100`), l'exit code rapporté est celui de `tail` (toujours 0), pas celui de la commande réelle | Correctif: pour toute commande longue dont le succès doit être vérifié, rediriger vers un fichier log (`cmd > log 2>&1; echo EXIT_CODE=$?`) plutôt que piper vers `tail`, et lire le marqueur EXIT_CODE explicitement — ne jamais faire confiance à une notification "completed" seule pour une commande pipée

- Symptôme: vérification `apt-cache policy` d'un paquet du catalogue applicatif (ex: `firefox-esr`, `chromium`) renvoie "Candidate: (none)" dans l'environnement WSL2 Ubuntu 22.04 de dev, laissant croire à un désync catalogue | Cause: WSL2 dev = Ubuntu 22.04, la distro CIBLE réelle de l'app est Debian (VM dédiée) — Ubuntu redirige plusieurs paquets courants (firefox, chromium) entièrement vers Snap et n'expose plus leur apt du tout, et manque des paquets plus récents présents sur une Debian à jour | Correctif: ne jamais utiliser `apt-cache policy` depuis WSL2 Ubuntu comme proxy pour vérifier/corriger le catalogue apt ciblant Debian — nécessite un accès à la vraie VM Debian ; si injoignable, documenter la limitation plutôt que de fabriquer un correctif basé sur le mauvais environnement
- Symptôme: `cand=$(commande | grep ... | awk '{print $2}')` retourne une chaîne vide de façon incohérente quand invoqué via `wsl.exe bash -lc "..."` depuis le Bash tool, alors que la même commande fonctionne en isolation | Cause: corruption `$()`/variable similaire au piège heredoc déjà documenté, pas limitée aux heredocs | Correctif: pour tout script shell avec substitution de commande/variables complexe destiné à WSL2, toujours l'écrire dans un fichier via l'outil Write puis l'exécuter via `wsl.exe bash -lc "bash '<chemin/mnt/c/...>'"` — jamais inline dans la chaîne `-lc`. Note : invoquer directement `wsl.exe bash '<chemin>'` (script en argument positionnel, pas dans `-lc`) échoue à cause de la réécriture de chemin Git Bash déjà documentée ; le chemin doit rester à l'intérieur de la chaîne `-lc`.
- Symptôme: impossible de vérifier en direct le comportement d'un outil externe non-privilégié (ex: `timeshift`, `efibootmgr`) car non installé dans l'environnement WSL2 de dev et aucun mot de passe sudo disponible pour l'installer | Cause: `apt-get install` nécessite root | Correctif: `apt-get download <paquet> [<dépendances>...]` télécharge le/les `.deb` SANS root (juste un fetch HTTP), puis `dpkg-deb -x <paquet>.deb dest/` extrait les fichiers sans les installer sur le système. Pour un binaire lié dynamiquement, extraire aussi ses bibliothèques partagées de la même façon (repérer les manquantes via le message d'erreur `error while loading shared libraries`, télécharger+extraire chacune, `LD_LIBRARY_PATH=dest/usr/lib/x86_64-linux-gnu` avant d'exécuter). Permet de reproduire le VRAI comportement (code de sortie, stdout, stderr) d'un outil sans jamais élever de privilège ni attendre un accès VM — a permis de résoudre en un seul cycle (107) une suspicion en suspens depuis 2 cycles (60, 98).
